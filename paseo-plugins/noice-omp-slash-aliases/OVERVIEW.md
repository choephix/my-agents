OMP slash commands for Paseo's `omp` provider: `/omfg <correction>`, `/queue <message>`, `/btw <question>` and, when switched on, `/tan <work>`. None of them cancels a running reply. They need the OMP extension `headless-builtins` (`~/workspace/my-agents/.omp/extensions/headless-builtins/`, symlinked into `~/.omp/agent/extensions/`). The plugin also gives every workspace **Instructions for the next chat** (below), which needs no OMP extension.

## Settings

**Settings → Host → Plugins → OMP slash commands → /tan command**, off by default (the Side agent plugin's `/tangent` is the replacement). It is a host setting; open apps follow a change at once.

- On: the plugin offers `/tan` in the `/` menu and sends it as `/follow-up /tan …`, as described below.
- Off: `/tan` is not in the `/` menu; OMP's own command list has no `tan` either (checked against its live list). Typed and sent anyway, the text goes to OMP as an ordinary message, and the extension's input hook still starts OMP's tangent, so it is not passed to the model. Without the `/follow-up` wrapper Paseo sends it like any message: in an idle chat that makes no difference; while a reply is running, Paseo stops that reply first (tested: the running `sleep` was aborted, then the tangent ran).
- Either way, `/tan` rows already in a chat, and the rows of a `/tan` typed while off, are drawn as below, and `tan.status` keeps working.

## How

- `/tan`, `/omfg` and `/queue` are composer aliases. OMP receives the `/follow-up` form (`/follow-up /tan …`, `/follow-up /omfg …`, `/follow-up <message>`), which Paseo sends out of band. The extension's input hook then runs OMP's real controller.
- Each `/tan` shows as **one row** instead of a chat bubble, because the main agent is never asked; OMP only tells it a tangent is running:
  - Your words sit on your side in a dashed bubble, muted until you hover over it.
  - Under it, the tangent's line: `tan`, its agent (`Tan-41b9`, the last 4 characters of OMP's id), the status (`running 0:42`, `done in 1m 50s`, `failed after 12s` in red, `stopped after 17s`) and a muted peek: what it is doing right now while it runs (its newest tool call by its intent, e.g. `bash · Running sleep 120`), otherwise the first line of its answer. Hovering over the agent name adds its model (`Tan-41b9 · claude-haiku-5-5`), once the tangent's first reply has named it.
  - Click the line to open it: while running, every step so far (the current one has a spinner), then the full agent id and model; afterwards the tangent's full answer as Markdown, then its full agent id, model and duration, and a Copy result button. Phones have no hover, so there the model shows only in the opened row. The line's own copy icon copies your text; it shows on hover on desktop and always on phones and native apps.
  - "Stopped" also covers a tangent cut off because its chat's OMP process was reloaded or closed (OMP aborts it).
  - The state comes from OMP's session files, read by the plugin's daemon side (`tan.status`): the chat's file from Paseo's agent record (`persistence.nativeHandle`), then the tangent's own `<chat>/Tan-<id>.jsonl` and OMP's `async-result` delivery. Running rows poll once a second, finished ones not at all.
  - Sources: in a live chat, Paseo's echo of the send (Paseo can echo it twice, as `/follow-up /tan …` and `/tan …`; one row is drawn). After a reload, and in a live chat at the agent's next turn when it was busy, OMP's `background-tan-dispatch` record; a live row for the same tangent wins, so it never shows twice.
  - Under Paseo the extension no longer posts "Dispatched background tan bg_N"; the row replaces it.
- `/btw <question>` asks OMP's own /btw engine, the same one behind OMP's RPC `btw` command. It uses the native prompt and the chat's full memory, including a reply that is still streaming. Nothing is added to the conversation, and the main reply keeps running. The client calls the plugin's daemon side (`btw.ask`), which sends `/follow-up /btw …`. The extension streams the answer to `$PASEO_HOME/omp-btw/<agentId>/<id>.json`. `PASEO_AGENT_ID` is the routing key, so an answer can only reach its own chat. The daemon side reads those files, and clients poll them (0.6 s while something is open or running, 4 s otherwise).
- The answers show in a sheet that opens as soon as you send `/btw`: a centred dialog up to 600 px wide on wide layouts, a panel at the bottom on phones. The plugin draws this sheet itself with React Native's `Modal`, because Paseo's plugin `Modal` always adds a 64 px title row. The sheet's only header is one 24 px line: "/btw · 4 · from this chat's memory, not added to it" (shorter on phones) and a small ✕. Escape, the ✕ or a tap on the dimmed backdrop closes it. Each question and its answer form a card with its own surface and border, set off from the sheet (darker cards on the dark sheet, white cards on the light sheet):
  - A header strip holds the muted question, always cut to 2 lines, and the time. Tap a long question to show it in full under the strip, and tap again to hide it.
  - The answer is Markdown at Paseo's small text size (13/19 px, the same size as the question) with Paseo's 12 px code (headings, lists, code, tables, links). Wide code blocks and tables scroll sideways.
  - A footer strip shows the status on the left: "Sending…", "Thinking… 0:03" or "Writing… 0:07" with a spinner, "Answered in 6s", "Stopped", or the error in red. **Stop** stays visible on the right while an answer runs. A finished answer has icon-only Copy and Dismiss buttons (accessibility labels "Copy answer" and "Dismiss"; Copy turns into a tick). On desktop they appear only while the pointer is over the card or one of them has keyboard focus. On phones and native apps they are always shown.
  - On web (desktop and phone), while you scroll a long card, its header strip (still the 2-line question) sticks to the top of the sheet and its footer strip to the bottom. Native apps have no sticky positioning, so there the strips scroll with the card.
  - Newest cards come first. The newest card and any running one are open; older cards fold to their header (the question, then the start of the answer). Tap a folded card to open it, or tap the chevron of an open card to fold it.

  A `btw` pill in that chat's composer reopens the sheet (tooltip "By the way (/btw)"). While an answer runs, its icon spins and it counts up (`btw 0:07`). With several answers it reads `btw · 4 answers`. Dismissing an answer hides it on every client, and Stop cancels and removes a running answer. Answers are also saved in OMP's own /btw history for the session.

  Phone layouts (under 600 px wide, the native phone apps) have no `btw` pill: the workspace ⋯ menu has a **By the way (/btw)** row listing the workspace's chats with answers (`Pricing · 2 answers`, `Pricing · answering…`, newest chat first; a single chat opens directly). Picking one shows its cards in that menu's bottom sheet, with Stop, Copy and Dismiss as in the sheet. Sending `/btw` still opens the sheet at once: for that, the chat's pill exists while the sheet is open (it sits behind the dimmed backdrop) and goes when you close it.
- The plugin hides the `/follow-up /btw …` message and Paseo 0.12's normalized `/btw …` echo from the timeline, because they are plumbing and not a conversation turn.
- Before sending, the plugin checks that the chat's live OMP process has the `/btw` handler. An agent started before the extension had `/btw` would otherwise pass the question to the model as an ordinary message. In that case you get: "This OMP agent started before /btw was installed. Reload or restart the agent" (`paseo agent reload <id>`, or close and reopen the chat).

Clients: web, desktop, iOS and Android. Only the public plugin API is used (slash commands, composer pills, header buttons, `Modal`, timeline transformers and renderers, plugin RPC, and the `agent.create`, `agent.created` and `workspace.archived` hooks), except the draft-tab `Instructions` pill, which is added to the web page directly. The Markdown renderer is plain React Native. It was tested live on the web only. Refresh or reopen an open app after installing or updating the plugin.

"OMP chats" means provider `omp` and every custom provider in `~/.paseo/config.json` whose `extends` chain reaches `omp` (e.g. `omp-nilo`, the nilo profile). Only the daemon side can read that config, so it answers `providers.omp` and checks it again before `/btw`; the client asks once and asks again about a provider it hasn't seen. That profile needs the `headless-builtins` symlink too (`~/.omp/profiles/nilo/agent/extensions/`). Other providers get the original slash command unchanged. Plugin commands win collisions with provider commands, and Paseo's built-in client commands win over plugins. These commands do not run with attachments (a Paseo limit).

## Instructions for the next chat

Text put into the system prompt of the next chat you start in a workspace, e.g. a long brief or a role. Unlike text in a message, it survives compaction.

- Every workspace header has an icon-only button "Instructions for the next chat" (on phones a row of the workspace ⋯ menu). It opens a popover (a bottom sheet on phones) with a text box, Clear and **Arm**, a muted line on what happens, and "Last used by “<chat>” at 14:05 · Copy into the box" once a chat has taken text from this workspace. Armed, the button reads `Instructions ✓` with an accent icon (phones: the row's title ends "· armed").
- Web and desktop, wide layouts: a draft tab ("New Agent", before its first message) has an `+ Instructions` pill right of Paseo's `Import session` pill; armed it reads `Instructions ✓` in the accent colour. It opens the same editor as a modal. Existing chats never show it, and sending the first message removes it with the draft. Native apps and phone layouts keep only the header/⋯ entry.
- Arming is per workspace and lasts 30 minutes; Clear disarms. The daemon side keeps it in `~/.paseo/plugin-data/omp-slash-aliases/next-chat.json` (with the last chat that took it), so a plugin reload or daemon restart keeps it. Archiving a workspace drops its entries (`workspace.archived` hook).
- When a chat is created in the workspace's directory, the plugin's `agent.create` hook disarms and sets the agent's own `systemPrompt` (appended after any existing one, with a blank line). Paseo saves it in the agent record and passes it to the provider on create and on every resume or reload, so it stays for the chat's life; it can't be changed afterwards. OMP gets it as `--append-system-prompt`.
- Providers: OMP (and `omp-nilo`), Claude Code, Codex, OpenCode and Pi take it: their Paseo 0.14 adapters pass `systemPrompt` on (checked live for OMP and Codex). Paseo's ACP adapter ignores it, so chats on any other provider (Copilot, Cursor, Grok, Antigravity, …) leave it armed for the next chat.
- Only chats you start: Paseo shows this hook the session config only (no labels, no caller). Chats started from the app have no title in it; agents started by agents (MCP `create_agent` requires a title), the side-agent plugin, schedules and `paseo run --title` have one, so they never take it. A `paseo run` without `--title` looks like yours: it takes the text, but when `agent.created` then shows a parent agent, the plugin re-arms it for your next chat (that agent keeps its copy). If a taken chat never shows up (its provider failed to start), the text is re-armed after 2 minutes.
- Importing a session doesn't go through `agent.create`, so imports never take armed text.
- Other clients see an arm or disarm when they come back to the foreground, when a chat appears in an armed workspace, and when they open the editor; nothing polls. Expiry is timed locally.
- The draft pill (`client/draft-button.ts`) is a copy of the `Import session` pill (Paseo has no plugin surface there), placed by the header button's icon while its workspace is on screen. It watches only `aria-selected` changes in the workspace screen (tab switches) and, while a draft tab is selected, that pane's child list; with no draft selected only the attribute watch is attached.

## Limits

- `/btw`: one question at a time per chat. This is OMP's own rule; a second question shows "A /btw question is still running; cancel it first". There are no follow-ups on an answer yet; OMP's engine supports them, but this UI does not. If an OMP process dies mid-answer, the answer shows as interrupted after 10 minutes. Answers and markers are kept for 7 days.
- Paseo's message-navigation rail (the small marks at the left edge) still counts the hidden `/follow-up /btw` message. Until a freshly loaded app has loaded its plugins, that message is briefly visible. `paseo logs` also shows it.
- Desktop web: once the sheet is open, the pill's "By the way (/btw)" tooltip can show next to it. The sheet is rendered inside the pill (the only per-chat plugin UI), so React passes hover events from the sheet up to the pill's tooltip trigger. The plugin cannot turn the tooltip off.
- Desktop web: the editor modal opened from a draft pill can show the header button's "Instructions for the next chat" tooltip, for the same reason (the modal lives in that button's icon). Its clicks and keys are stopped there so they don't open the header popover too.
- The sheet is drawn by the plugin with React Native's `Modal`, not Paseo's sheet. On phones it is a plain panel without swipe-to-close, and it uses Paseo's default UI font, so a custom UI font set in Paseo's settings is not applied there.
- Phone layouts: while a `/btw` sheet is open, its host pill shows behind the dimmed backdrop (Paseo mounts no hidden pill's icon, and the icon is the only per-chat host). The ⋯ menu rows need no host.
- The ⋯ rows (`client/phone-menu.tsx`, shared with other noice plugins) are Paseo header buttons, which belong to a workspace and don't know the open tab; hence the list of chats.
- `/tan` has no MCP tools.
- `/tan`: OMP's "Background job bg_N has completed. Resume your work using the result below." notice stays under the row. Paseo 0.12 does not let plugins transform notifications (transformer item types: user and assistant messages, reasoning, tool calls, todos, errors, compaction), and the notice comes from OMP itself. Paseo also keeps only its first line; the full result is in the row.
- `/tan` in a reloaded chat: a tangent sent while the agent was busy is listed at the agent's next turn, because that is where OMP records it. A live chat shows it where you sent it.
- `/tan`: the tangent's file is matched to Paseo's echo by time (they are written within milliseconds; window 10 s), since the echo carries no id.
- `/omfg` shows OMP's save-location question but not its draft-rule panel; check the saved file. Generation can take a while.
- This depends on OMP internals (controller and `rpc-btw` modules; the session-file entries `session_init`, `session_exit`, `async-result`, `background-tan-dispatch`) and on Paseo 0.12 behaviour (`/follow-up` out of band, the `/tan` echoes, `PASEO_AGENT_ID` in the provider environment).

Disable with `paseo plugin disable noice-omp-slash-aliases`. To keep the plugin but drop the OMP side, remove the `headless-builtins` symlink from `~/.omp/agent/extensions/`. Without it, the commands reach the model as plain text. Instructions for the next chat don't depend on it.

## Development

`npm install`, `npm test` (vitest), `npm run typecheck`. The tests cover the Markdown parser and its one-line preview, ask/answer correlation and routing across chats, the timer and duration labels (`client/btw-store.test.ts`), the file contract with the extension's real writer (`server/btw-outbox.test.ts`), the live-process readiness check, and the /tan state from session files (`server/tan-sessions.test.ts`: the tangent's own part of its file, step names, delivery vs. own exit, stopped when no OMP process could run it, splitting multi-job deliveries, matching by start time, files that grow mid-line). `paseo plugin reload noice-omp-slash-aliases` applies edits.
